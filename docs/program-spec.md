# Heirloom program spec (source of truth for contract, IDL and TS client)

Every agent builds against this file. If you must change it, change it here first and say so in your report.

- Program name: `heirloom` (Anchor 1.2.2, Rust). Program id: **`b3PBVwkLnyx7eyLPNtc5J3Ds3os3cenqCVRHaCJM7FY`**
  (keypair at `target/deploy/heirloom-keypair.json`, gitignored; keep that file to keep the id). The TS side reads
  `NEXT_PUBLIC_HEIRLOOM_PROGRAM_ID`. The IDL is `app/src/lib/chain/idl/heirloom.json` (generated by `anchor build`).
- Money: USD₮ SPL token, 6 decimals. All amounts are `u64` base units (1 USD₮ = 1_000_000).
- Times: `i64` unix seconds from `Clock`.
- Hashes: `[u8; 32]` SHA-256 of the off-chain file/JSON. No personal data on-chain, ever.
- Token transfers use `transfer_checked` (token program = classic SPL Token; Token-2022 not required).
- Bitmaps: verifier index i (0..3) sets bit `1 << i`. Count with `count_ones()`.

Signer roles: **owner** (estate.owner), **agent** (estate.agent), **verifier** (one of estate.verifiers), **beneficiary** (wallet with an active Beneficiary PDA), **buyer**, **anyone**.

**Living plans** (added 2026-11-11): a `starts_now` rule already works while the owner is alive (estate Active): claims need the agent + the **owner** (`owner_approve_claim`), verifiers alone are not enough; after unlock the verifier quorum (or an earlier owner approval) counts. Scheduled payments (`recurring_amount > 0`) are paid by anyone calling `execute_scheduled` once due. No minimum interval or waiting period: 60 s works for devnet demos.

Losing offers are returned by the buyer calling `withdraw_offer` (works in any asset state).

### Clarifications made while implementing (contract author, 2026-11-11)
- `submit_death_claim`: `cert_hash` must be non-zero (NoDeathClaim) and only one open claim at a time: fails with
  BadStatus if `death_cert_hash ≠ 0` (stops a second submission resetting attestations). A rejected or vetoed claim clears it.
- `review_death`: also requires status Active and `death_verdict == Pending` (BadStatus), so the agent can't re-review after DeathPending.
- `attest_death`: also requires a claim (NoDeathClaim); allowed in Active **or** DeathPending; only the attestation that
  reaches `death_threshold` starts the timer (later attestations don't reset `death_pending_since`).
- `create_estate` vault, `place_offer` escrow: `init_if_needed` (anyone can pre-create an ATA, which would otherwise block the call).
- `execute_claim`: also checks estate status (see row 18). `approve_hardship`: also requires asset not Sold (BadStatus).
- `list_asset` wrong signer → NotAgent; `duration_secs > 0` (InvalidAmount). `add_rule`: Beneficiary PDA must be active (NotBeneficiary); bad caps → InvalidAmount.
- `register_asset`: nft mint needs decimals 0 **and** supply 1 (InvalidNft); bad prices → InvalidAmount.
- `withdraw_offer` / `accept_offer` move the whole escrow balance (≥ offer.amount) so the escrow close can't fail.
- Mint checks: `usdt_mint` account `address = estate.usdt_mint` and every owner/buyer USD₮ token account `mint == estate.usdt_mint`, both → WrongMint.

## Off-chain hashing convention
`hash = sha256(bytes)`; for JSON use canonical JSON (keys sorted, no whitespace). Shown in UI as hex.

## Account names the TS client resolves (added by the backend agent, 2026-11-11)
`app/src/lib/chain/instructions.ts` resolves accounts **by name from the IDL** (case/underscore-insensitive), so any order works,
but names must be one of these. Preferred name first; aliases in brackets also work.
- Signers: `owner`, `agent`, `verifier`, `buyer`; beneficiary-signed ixs (submit_*): `beneficiary` = signing wallet + `beneficiary_account` = Beneficiary PDA (as in the IDL); `finalize_unlock` / `execute_claim`: `payer` [`signer`]; `list_asset`: `authority` [`signer`].
- PDAs: `estate`, `beneficiary` (the Beneficiary PDA in add_rule), `payee` (Payee PDA), `rule`, `claim`, `asset`, `offer`, `hardship`.
- Plain wallets (unchecked): `wallet` (add_beneficiary/add_payee), `payee_wallet`, `recipient` (accept_offer USD₮ receiver).
- Mints: `usdt_mint` [`mint`], `nft_mint`.
- Token accounts: `vault`, `owner_usdt` [`owner_token`, `owner_ata`], `owner_nft`, `nft_escrow`, `offer_escrow` [`escrow`], `buyer_usdt` [`buyer_token`], `buyer_nft`, `payee_usdt` [`payee_token`], `recipient_usdt` [`recipient_token`].
- Programs: `system_program`, `token_program`, `associated_token_program`, `rent` (fixed addresses in the IDL are used as-is).
- Args are passed **positionally in the order listed in the table above**, so arg names may differ.

### Decisions where guardians-spec.md left a gap (contract author, 2026-11-14)
- **Objections need real, current targets:** a Claim/Hardship objection needs the watched holder's approval bit on it (monitors
  watch approvals; they can't freeze arbitrary items). An objection may be raised any time the target is still open, not only inside the window.
- **One Objection PDA per target, re-usable:** with seeds `["objection", target]`, seats, assets, the estate and the guard could only
  ever get one objection. A resolved objection is therefore overwritten by a new one (the events keep the history); a Dismissed
  objection on a one-off Claim/Hardship can't be re-raised.
- **Upheld Sale** sets the asset back to Held (the "blocked until relisted" rule). **Upheld Hardship** also withdraws the hardship floor.
- **Fallback objections:** every holder is gone and the owner is dead, so **monitors** vote (bitmap `1 << (2·seat + slot)`); 2 decide.
- **Fallback objections lapse (funds are never locked forever; product owner, 2026-11-14):** an Open Fallback objection
  not Upheld by `raised_at + fallback_wait_secs` lapses and counts as Dismissed. After that, votes on it fail (`ObjectionLapsed`).
  Anyone may call `lapse_objection` (Fallback kind only; BadStatus otherwise or if not Open; `ObjectionNotLapsed` if too early)
  to mark it Dismissed, which decrements open_objections and emits ObjectionResolved (upheld = false). `execute_fallback`
  does the same itself when it finds a lapsed objection, so its `objection` account is now **writable**. A lapse does not restart
  the countdown. A dismissed or lapsed Fallback objection can't be re-raised in the same countdown (raised_at ≥ fallback_started_at
  → BadStatus); a restart (upheld objection, or a new recipient after a proven death) allows a new one. Upheld still resets the fallback.
  Instruction `lapse_objection` (no args, anyone): accounts estate, guard(w) `["guard", estate]`, objection(w) `["objection", guard]`.
  New errors: `ObjectionLapsed 6040`, `ObjectionNotLapsed 6041`.
- **Owner signs of life void a started fallback:** `execute_fallback` requires `estate.last_heartbeat < fallback_started_at`
  (heartbeat / veto_death update it), and `start_fallback` may restart a voided countdown. `set_fallback` also resets it.
- **Fallback deaths:** the Guard has no field for a pending report, so `report_fallback_death` only emits an event; the agent's approval
  sets the bit and restarts a running countdown, so family get the full wait to object to the new recipient.
- **Succession:** the wait runs from the confirmation. A backup who reported or confirmed the death is never promoted; a backup
  who has become another seat's holder is skipped (no duplicate verifiers). A monitor who becomes the holder is dropped as monitor.
- **ApprovalStamp** is created (init_if_needed) on every claim's first approval, Guard or not (about 0.0012 SOL rent, paid by `payer`),
  so a Guard added later still finds stamps. Claims approved before this upgrade have no stamp: with a Guard they need one more
  verifier approval (which writes the stamp) before they can execute.
- **Owner-approved claims** (living plans, owner alive) skip the objection window but still stop on an Open objection.
- `start_fallback` / `execute_fallback` need all three Seat accounts, so the owner must create all three seats.
- `execute_fallback` sets the estate status to Unlocked (it may still be Active with an agent-approved death claim).
- Errors beyond the spec list: `BadFallback` (appended last). Events beyond the spec list: `GuardInitialized`, `SeatConfigured`,
  `SeatDeathVetoed`, `ObjectionVoted`, `FallbackDeathReported`, `FallbackDeathReviewed`.

### Disputes (U9)
Reuses the guardians' objection pattern instead of duplicating it: a **dispute is an `Objection` account in the same
`["objection", target]` PDA with `seat_index = DISPUTE_SEAT = 254`** (`monitor` = the disputer). Every check that
already pauses on an open objection (`execute_claim`, `finalize_unlock`; also `accept_offer`, `finalize_succession`)
therefore pauses on an open dispute too, and a target has a monitor's objection or a dispute, never both.
Differences from a monitor's objection: no Guard is needed (works on every estate), it can be raised by an active
beneficiary or a verifier, it is resolved only by 2 of 3 verifiers (`resolve_dispute`; never by `vote_objection`, never by
the owner alone), and it **lapses** at `raised_at + max(estate.waiting_period_secs, 60)`: an Open dispute past that time
counts as Dismissed everywhere (`objection_is_open` and `raise_objection` are lapse-aware), and votes on it fail with
`DisputeLapsed`. Funds can therefore never be locked by a dispute.

| Instruction | Args | Signer | Rules |
|---|---|---|---|
| `raise_dispute` | kind TargetKind, target Pubkey, reason_hash [u8;32] | `disputer`: a verifier, or an active beneficiary (passes `beneficiary_account`) (NotDisputer) | reason_hash ≠ 0 (InvalidAmount). Claim: `target_account` = the Claim, same estate, status Open. Unlock: target = estate, status DeathPending. Other kinds → BadStatus (monitors cover sales, hardship, successions, the fallback). An effectively open objection/dispute on the target → ObjectionOpen. **One challenge per claim**: any earlier record on a claim → BadStatus. **One per waiting period**: an earlier non-upheld record on the estate raised at or after `death_pending_since` → BadStatus. Emits `DisputeRaised` |
| `resolve_dispute` | uphold bool | `verifier`, not the disputer (NotVerifier) | is a dispute and Open (BadStatus); not lapsed (DisputeLapsed); one vote each (AlreadyApproved); 2 uphold → Upheld: Claim → Rejected; Unlock → death claim cleared, estate Active (same code as an upheld objection). 2 dismiss → Dismissed. Emits `DisputeVoted`, `DisputeResolved` |

Accounts: raise_dispute: disputer(w,s), estate, beneficiary_account(o), target_account(o; Claim only), objection(w), system_program.
resolve_dispute: verifier(s), estate(w), objection(w), target_account(w,o; Claim only).

### Yearly caps
`YearCap` `["yearcap", rule]`: rule, cap u64, period_start i64, period_spent u64, bump. The period is 365 days and
rolls forward by whole periods (spend restarts at 0). A rule without a YearCap has no yearly cap.

| Instruction | Args | Signer | Rules |
|---|---|---|---|
| `set_yearly_cap` | cap u64, period_start i64 | owner, estate Active (BadStatus) | 0 < cap ≤ lifetime_cap and cap ≥ recurring_amount; 0 ≤ period_start ≤ now (InvalidAmount). period_start 0 = now for a new cap / keep the period for an existing one. Spend already recorded is kept. Emits `YearlyCapSet`. Accounts: owner(w,s), estate, rule, year_cap(w), system_program |

Enforced (new account `year_cap` = `["yearcap", rule]` appended, may not exist): `submit_claim` (checks), `execute_claim`
(re-checks and records, writable), `execute_scheduled` (checks and records, writable; an instalment over the cap fails
with `ExceedsYearlyCap` and stays due until the next period).

### Sponsorable permissionless calls
`finalize_unlock`, `finalize_succession`, `start_fallback` and `lapse_objection` now end with `caller: Signer` (any wallet;
it gains no rights). The fee sponsor can pay as fee payer while the user signs as caller, so the sponsor policy's
checks (≥ 1 user signature, sponsor never inside an instruction, allow-listed discriminator, rate limit per signer) all
still apply. `raise_dispute`, `resolve_dispute`, `set_yearly_cap` are on the sponsor allow-list; the agent signs none of them.
